Agentic workload

  • About 100 prompt tokens per output token
  • Each turn repeats the previous prompt
  • The agent waits for the whole response
  • REASONING, then ACTING, then again

Between turns the engine sees the session as idle. Its KV blocks are still valuable.

Saturation detection

  • Track every session's KV footprint in tokens
  • Working set = all sessions on the pod, running or idle
  • Saturated = working set > KV capacity
  • Idle footprint decays for admission: 2^-t

Engine KV utilization cannot do this. It counts running requests only; idle sessions look free.

7

Admission order

  1. Admitted session: pass through, always
  2. Not saturated: new session to the pod with most room
  3. Saturated: pause idle sessions, smallest first
  4. Held requests wait in the router; paused first, then new
  5. Backstop: admit after 1800 s anyway
8

Design in llm-d: one plugin, four extension points

Simpler than the Python router. Admission runs on every dispatch cycle, not every 5 s. A client disconnect returns the session to idle.
Pause sweep. Runs inside the Saturation hook, per pod, at most every pauseSweepSeconds. No background thread.
Session ledger. Same idea as the session-state-producer of llm-d-router issue 2524, plus the KV fields.

Summary

  • Placement does not help; admission control does
  • 1.54x on one pod, 1.42x on four, TTFT p50 12x to 33x lower
  • Cost: a long tail for a few sessions
